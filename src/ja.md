# コンポーネントの依存関係管理：課題と解決策

Abir HSAINI（4D Inc. テクニカルサービスエンジニア）

テクニカルノート 25-06

## 概要

プロジェクトの依存関係（dependencies）を通じて4Dコンポーネントを管理する場合、開発中にさまざまな課題が生じることがあります。特に問題となるのが、バージョン管理と更新の一貫性です。これらの問題は、予期しない動作や、プロジェクト間での統合の難しさにつながる可能性があります。

このテクニカルノートでは、4Dコンポーネントを扱う際にデベロッパーが直面しやすい問題をまとめ、それらを軽減するための推奨されるベストプラクティスを紹介します。効果的な依存関係管理の方法をより明確に理解し、安定していて保守しやすい4Dアプリケーションを実現することが目的です。

## はじめに

**4Dコンポーネント**とは、プロジェクトに特定の機能を追加するために設計された、再利用可能な4Dコードのパッケージです。デベロッパーは、コードをモジュール化するために独自のコンポーネントを作成することも、4Dコミュニティが開発したコンポーネントを組み込むこともできます。コミュニティのコンポーネントは、GitHubなどのプラットフォームで公開されていることがよくあります。

4Dには、**4D SVG**、**4D NetKit**、**4D View Pro**、**4D Write Pro Interface**などのビルトインコンポーネントも用意されています。これらは、グラフィックの描画、メール連携、スプレッドシート処理、リッチテキストドキュメントの編集といった高度な機能を提供します。これらのコンポーネントを使用すると、強力な機能でアプリケーションをすばやく拡張できます。

しかし、プロジェクトの規模と複雑さが増すにつれて、コンポーネント間の依存関係の管理は難しくなります。よくある問題としては、厳密なバージョン要件、インタープリターモードとコンパイルモードでの動作の違い、ときおり失敗する更新処理などが挙げられます。

このテクニカルノートでは、これらの課題を取り上げ、4Dアプリケーションでコンポーネントの依存関係を安定して確実に管理するための実践的な推奨事項を紹介します。

## 4Dにおける依存関係管理を理解する

### JSONファイルによるプロジェクトの依存関係の扱い

4Dプロジェクトでは外部のコンポーネントを使用できます。依存関係は、わかりやすく柔軟な方法で管理することが重要です。4Dは、**dependencies.json**と**environment4d.json**という2つのJSONファイルを作成します。

これらのファイルは連携して、プロジェクトに必要なコンポーネントと、そのコンポーネントを4Dがどこで見つけるべきか（ローカルに保存されているか、GitHubなどのオンラインでホストされているか）を定義します。

#### 1. dependencies.json：必要なコンポーネントの宣言

**dependencies.json**ファイルは、プロジェクトに必要なすべての外部コンポーネントを宣言する中心的な場所です。コンポーネントがローカルに保存されている場合もリモートでホストされている場合も、プロジェクトを開くたびに4Dが正しいコンポーネントを読み込むようにします。

このファイルは、プロジェクトパッケージ内の次のパスに**配置する必要があります**：

```text
/TheProject/Project/Sources/dependencies.json
```

宣言できるコンポーネントは次のとおりです：

- **ローカルコンポーネント**：マシン上の標準のComponentsフォルダーに保存されているもの
- **GitHubベースのコンポーネント**：パブリックまたはプライベートのGitHubリポジトリから取得するもの

例：

```json
{
    "dependencies": {
        "theGitHubComponent1": {
            "github" : "JohnSmith/theGitHubComponent1"
        },   // GitHub-based component
        "theLocalComponent2" : {}  // Local component
    }
}
```

この例では、プロジェクトに2つのコンポーネントが必要です。1つはローカルに保存されたもの（theLocalComponent2）、もう1つはGitHubから取得するもの（theGitHubComponent1）です。このように明確に宣言しておくと、異なる環境でも同じ構成を再現しやすくなります。

「theLocalComponent2」のパスは、ここ（dependencies.json）で定義することも、次の項で説明するenvironment4d.jsonファイルで定義することもできます。

#### 2. environment4d.json：コンポーネントのパスのカスタマイズ

dependencies.jsonファイルは必要なコンポーネントを定義し、environment4d.jsonファイルはそれらのコンポーネントの場所を指定します。environment4d.jsonを使用すると、コンポーネントのデフォルトのパスを上書き（オーバーライド）できます。これは、チームでの開発や複数のプロジェクトを扱う構成で特に役立ちます。

このファイルは任意ですが、次のような場合にきわめて便利です：

- 複数のプロジェクトで同じコンポーネントを使用する場合
- 開発中やテスト中に、GitHubコンポーネントのローカル版を使用する場合
- ローカルのパスをバージョン管理の対象外にして、リポジトリをクリーンで移植しやすい状態に保つ場合

**environment4d.json**ファイルは、次の場所に配置できます：

- プロジェクトのルートフォルダー
- プロジェクトより上位にある任意の親フォルダー（4Dはファイルが見つかるまで上位の階層を検索します）

プロジェクトフォルダーの外に保存されているローカルコンポーネントを使用するには、environment4d.jsonファイルでそのパスを定義できます。これにより、コンポーネントがコンピューター上の別のフォルダーに置かれていても、4Dはそれぞれのコンポーネントの場所を把握できます。

相対パスと絶対パスのどちらもサポートされています。通常は相対パスを使用することをお勧めします。プロジェクトの移動や共有、Gitなどのソース管理システムへの保存が容易になるうえ、マシンごとに異なる固定のファイルの場所に起因する問題も避けられるからです。

例：

```json
{
    "dependencies": {
        "theLocalComponent1" : "theComponent1",
        "theLocalComponent2" : "../theComponent2",
        "theLocalComponent3" : "file:///Users/jean/theComponent3",
        "theGitHubComponent1": {
            "github" : "JohnSmith/theGitHubComponent1"
        }
    }
}
```

4Dがコンポーネントを探す場所は、主に3つあります。1つ目はプロジェクトディレクトリ内のComponentsフォルダー、2つ目はdependencies.jsonファイルに記載されたパス、3つ目はenvironment4d.jsonファイルで設定されたカスタムパスです。コンポーネントを読み込む際、4Dは優先度が最も高いComponentsフォルダーを最初にチェックします。次に、environment4d.jsonのカスタムパスが設定されていればそれを使用します。このパスはdependenciesファイルのパスより優先されます。これらの場所でコンポーネントが見つからない場合、4Dは4D NetKitや4D SVGなどのビルトインコンポーネントを読み込みます。この順序によって、環境に応じて正しいコンポーネントが読み込まれます。

### 「プロジェクト依存関係」機能による依存関係のモニタリング

dependencies.jsonファイルやenvironment4d.jsonファイルを使用する以外に、依存関係パネルを使用して依存関係を管理する簡単な方法もあります。依存関係パネルは、**デザイン**／**プロジェクト依存関係**メニューから表示できます。

このグラフィカルインターフェースを使用すると、JSONファイルを手作業で編集しなくても、4D内でプロジェクトの依存関係を追加、削除、更新、モニタリングできます。コンポーネントをより視覚的かつ直感的に管理できるため、開発中やデバッグ中に特に役立ちます。

![](fig-01)

4Dの依存関係パネルには、オリジン（由来）にかかわらず、プロジェクトで使用されているすべての依存関係が表示されます。各依存関係の名前の下にはオリジンタグ（origin tag）が表示され、そのコンポーネントがどこから読み込まれたかを示します。

| オリジンタグ | 説明 |
|---|---|
| **4Dビルトイン** | 4DアプリケーションのComponentsフォルダーにあるビルトインの4Dコンポーネント |
| **プロジェクトで宣言** | プロジェクトのdependencies.jsonファイルで宣言されたコンポーネント |
| **environmentで宣言** | environment4d.jsonファイルで定義されたコンポーネント |
| **Componentsフォルダー** | プロジェクトのComponentsフォルダー内に実際に置かれているコンポーネント |

#### 1. 依存関係の追加

依存関係を追加するには、まずパネルのフッターにある［+］ボタンをクリックします。次に、ソースとしてローカルシステムかGitHubのどちらかを選択できます。

![](fig-02)

ローカルコンポーネントの場合、選択した項目が有効で、プロジェクトフォルダーと同じ階層にあれば、dependencies.jsonファイルでのみ宣言されます。一方、プロジェクトフォルダーと同じ階層にない場合は、そのファイルパスがenvironment4d.jsonファイルにも記述されます。

![](fig-03)

GitHubコンポーネントの場合は、**GitHubリポジトリ**のアドレスを入力し、バージョンの解決方法を制御する**依存関係ルール**を定義する必要があります。これらは、コンポーネント管理ダイアログで設定します：

![](fig-04)

- **リポジトリ**：GitHubのパスを「オーナー/リポジトリ」の形式で指定します。
- 依存関係ルール：
    - 自動更新する(latest)：latestタグの付いた最新のリリースをダウンロードします。
    - メジャー更新の手前まで：同じメジャーバージョンの範囲内でコンポーネントを更新します。
    - マイナー更新の手前まで：マイナーバージョンの変更のみに更新を制限します。
    - 自動更新しない(タグ指定)：タグで指定した特定のバージョンをダウンロードします。
    - 4Dのバージョンに追随する：使用中の4Dのバージョンに対応するリリースをダウンロードします。リリースが4Dの命名規則に従っていることが前提です。

この設定により、コンポーネントの互換性とバージョンを柔軟に管理できます。

#### 2. GitHub依存関係の更新

4Dの依存関係マネージャー（Dependency Manager）には、**GitHubコンポーネントの更新のチェックと更新**を**自動**または**手動**で行う機能が組み込まれています。

- 新しいバージョンの**自動チェック**は、バックグラウンドで実行されます。GitHubのアクセストークンを登録しておくと、チェックの頻度が高くなります。

![](fig-05)

- 更新の**手動チェック**：
    - **単一の依存関係**の場合：右クリックして、*更新をチェックする*または*次回起動時に更新*を選択します。
    - **すべての依存関係**の場合：パネル下部のオプションメニューを使用します。

（バージョンのルールに基づいて）更新が検出されると、ステータスが表示されます。デベロッパーは、その更新を適用するか無視するかを選択します。

![](fig-06)

更新を開始すると、新しいバージョンを読み込むためにプロジェクトの再起動を提案するダイアログが表示されます。再起動を後回しにした場合は、次回の起動時に更新が行われます。

## インタープリターモードとコンパイルモードの違い

4Dの**コンポーネント**には**インタープリター**版と**コンパイル済み**版があり、この違いによってホストプロジェクトでの使い方が決まります。

**インタープリター版コンポーネント**には、コンパイルされていないソースコードが含まれています。このコンポーネントは、**インタープリターモードで実行されている4Dプロジェクト**でしか使用できません。その構造は標準的な4Dプロジェクトフォルダー（たとえば`theComponent.4dbase`という名前のフォルダー）と同様で、メソッド、フォーム、リソースなど、すべてのプロジェクトファイルが含まれます。コンポーネントとして認識させるには、このフォルダーをホストプロジェクトの`Components`フォルダーに配置する必要があります。

一方、**コンパイル済みコンポーネント**には、`.4DZ`ファイルにコンパイル済みのコードが含まれています。このタイプのコンポーネントは**インタープリター**と**コンパイル済みのプロジェクト**のどちらでも使用できるため、より柔軟で、配布（デプロイ）にも適しています。メインのプロジェクトをコンパイルモードで実行する場合は、コンパイル済みコンポーネントだけを使用する必要があります。

より簡単な構造として、.4DZファイルをコンポーネントフォルダーのルートに直接置き、必要に応じてResourcesフォルダーとInfo.plistを添える方法もあります。ただし、この簡易な構造はmacOSの公証（notarization）の要件にはあまり適していません。

## タグとバージョン

4DでGitHubコンポーネントを扱う場合、各リリースには一意のタグとセマンティックバージョン番号が関連付けられます。これらの識別子を使用して、プロジェクトで使用するコンポーネントのバージョンを指定できます。dependencies.jsonファイルまたはenvironment4d.jsonファイルでは、特定のタグ（例："tag": "beta2"）またはセマンティックバージョン（例："version": "2.1.3"）を定義できます。バージョンの表記はセマンティックバージョニング（Semantic Versioning）の形式「major.minor.patch」に従います。バージョンの範囲やワイルドカードを使用して、柔軟な依存関係を定義することもできます。

たとえば、"1.*"はメジャーバージョン1のすべてのバージョンを対象とし、">=1.2.3"は1.2.3以降のすべてのバージョンを含みます。^や~の接頭辞もサポートされており、互換性のあるバージョンの範囲を指定できます。タグもバージョンも指定しない場合は、GitHubで利用できる最新のリリースが自動的に取得されます。

```json
{
    "dependencies": {
        "theFirstGitHubComponent": {
            "github": "JohnSmith/theFirstGitHubComponent",
            "version": ">=1.2.3"
        }
    }
}
```

「4Dのバージョンに追随する」依存関係ルールを選択する場合は、GitHub上のコンポーネントのタグが特定の命名規則に従っている必要があります。これにより、4Dはタグとプロジェクトのバージョンを正しく対応付けることができます。

![](fig-07)

LTS（Long Term Support）版の場合、タグは**x.y.p**のパターンに従う必要があります。**x.y**は追随するメインの4Dバージョン、**p**は任意のパッチを表します。たとえば、**20.4**を指定すると、依存関係マネージャーは**20.\***に該当する最新のコンポーネントバージョン、または20未満のバージョンを取得します。

![](fig-08)

Rリリース（R-Release）の場合、タグの形式は**xRy.p**で、たとえば**20R9.1**のようになります。この場合は**20R10**未満の最新のコンポーネントバージョンが検索されます。該当するリリースが見つからない場合は、4Dが通知を表示します。これらの規則によって、依存関係の更新をプロジェクトの4Dバージョンの方針に合わせることができます。

## よくある問題と解決策

依存関係マネージャーで依存関係を管理していると、いくつかの問題が発生することがあります。この章では、実際のプロジェクトでよく見られる問題を取り上げ、その解決策と、問題を防止または解決するためのベストプラクティスを紹介します。

### コンポーネントの更新が検出されない、または再起動後に適用されない

GitHubコンポーネントに更新があるはずなのに「Update available」（更新あり）のメッセージが表示されない、あるいはプロジェクトを再起動しても更新が適用されないことがあります。1つ目の原因として、自動アップデートオプションが無効になっている場合が考えられます。この場合、新しいバージョンがあっても更新は自動的に適用されません。デベロッパーはコンポーネントを右クリックして「次回起動時に更新」を選択し、プロジェクトを再起動して更新を適用する必要があります。2つ目に、更新がまったく検出されない場合は、GitHub上のそのバージョンが**最新リリース（latest）としてタグ付けされていない**可能性があります。4DはGitHubのリリースタグを使用して更新を検出するため、使用したいバージョンが正しく公開またはタグ付けされていないと、依存関係マネージャーはそれを有効な更新として認識しません。

### 「The download archive does not contain a valid dependency」エラー

![](fig-09)

このエラーは通常、GitHubコンポーネントを読み込もうとしたときに、ダウンロードしたアーカイブの構造を4Dが有効なコンポーネントとして認識できない場合に、依存関係マネージャーに表示されます。

最も多い原因は、GitHubのリリースに関連付けられたZIPアーカイブが正しい構造になっていないことです。4Dは、アーカイブのルートに有効な4Dコンポーネントが直接含まれていることを想定しています。アーカイブに余分な最上位フォルダーがあったり、コンポーネントが深い階層に置かれていたりすると、4Dは必要な構造を見つけられず、このエラーが発生します。

![](fig-11)

最新のリリースが存在することを確認してもエラーが解消しない場合は、アクセストークンが正しくない可能性があります。その場合は、依存関係マネージャーから「GitHub**パーソナルアクセストークン**を編集...」をクリックして、トークンを修正します。

### 明示的に許可していないのにコンポーネントのバージョンが変わる

アプリケーションを**開発モード**で実行していると、手動でチェックを要求していなくても、4Dは**アプリケーションの起動から約3分後**にバックグラウンドのスクリプトを自動的に実行して、コンポーネントの更新をチェックします。

新しいバージョンが見つかると、4Dは更新があることを通知します。しかし、デベロッパーがこの通知に気付かずに（**自動アップデートが有効**な状態で）データベースを再起動すると、確認なしに新しいバージョンが自動的にインストールされます。

## まとめ

4Dプロジェクトで依存関係を管理するには、特にGitHubの外部コンポーネントを使用する場合、体系的な構成と細部への注意の両方が必要です。このノートでは、dependencies.jsonとenvironment4d.jsonを使用して依存関係を宣言する方法、依存関係マネージャーで依存関係をモニタリングしてトラブルシューティングする方法、そして更新とバージョンを正しく扱う方法を説明しました。
